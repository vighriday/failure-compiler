How This Works, In Plain Language

The app is a browser page talking to a small Python server running on your laptop. The server binds to 127.0.0.1 only, because it holds AI keys in memory.

When you paste a plan, the server sends it to an AI (Gemini first, Groq as a fallback). The AI reads messy text and returns a structured description of the plan: who is doing what, in what vehicle, at what place, between what times. The AI returns an AIPlanReading. The server wraps it into a PlanMap, adding its own metadata. The two schemas are separate so Groq strict mode never forces the AI to invent a fingerprint or a fix history.

That description comes back as JSON and the server runs it through a strict format check before it touches anything else. This is the core learning goal made concrete: the AI produces output, the gate decides whether it is usable, and nothing downstream ever sees an unchecked map.

The browser calls POST /api/update-map on every correction against the server-owned draft, using the same Python rules that run at Confirm. Rules are implemented once. No TypeScript reimplementation.

The checker is a constraint solver (CP-SAT). Singles run first. Any pair that contains a broken single is marked dimmed without solving. For remaining pairs, the solver finds the best possible schedule using only the people and vehicles the plan names. Zero lateness proved = tick. Minimum above zero proved = cross, with that minimum as the human cost. Some scenarios leave a route with no driver or the loading area with no key holder; rather than failing with no number, every route may be "not delivered," carrying a penalty larger than any possible lateness (households times the full horizon). Unproved or ambiguous outcomes return a question mark; proved outcomes state their human cost. Deterministic time limit hit = question mark, never a pass.

After the format gate, the server normalises all entity ids to stable slugs from type and name (person-ravi, vehicle-van, route-c) and updates every reference. Unchanged extracted labels and checker inputs normalize consistently when only AI-assigned IDs change. Different names can produce different person/vehicle IDs; reading equivalence is scored separately after role alignment.

Clicking a cross triggers one AI call that returns both a plain explanation sentence and up to three fix suggestions. The server caches the result per fingerprint and scenario, so reopening a cross never calls the AI again. The checker's facts are always shown; the AI sentence sits next to them, labelled. Turned-down reasons come from the checker. Preview draws from stored fix results without re-solving.

available_until reduced by size. E.g. "Sam leaves 90 min early."

The Validation Gate prd.md › Plain Rules Validation

The learning goal made concrete: AI produces output → gate checks it → human confirms → checker acts. Every AI output passes through the same gate.

1
Parse JSONMalformed JSON rejected immediately with the parse error.
2
Pydantic validationextra="forbid", all fields required. Missing field, extra field, wrong type: rejected with the field name.
3
Reference integrityEvery person, vehicle, place id used in routes and jobs must exist in the entity lists. Unknown id rejected with the offending value.
4
Plain rulesEvery route has a driver id and a vehicle id. Every time is coherent. Finish time is explicit. Problem count within cap. Failures surface as questions on Screen 2; never silent.
5
Human confirmsConstrained inputs only. Every correction triggers POST /api/validate-map (debounced 150 ms, same Python rules). Affected items lose their confirmed mark. Confirm button computed from live state.
6
Server re-validates on ConfirmBrowser call is for speed; server is the authority. Checker endpoint refuses any map that fails.

Rules re-run on every change, not only at Confirm. Entities are referenced by internal id. If a correction changes something other items depend on (e.g. Ravi corrected to "can't drive"), those items lose their confirmed mark and show "check this, Ravi changed." The whole map is re-validated from scratch each time.

Fixes go through the same gate. A fix that fails shows as "Couldn't apply" with the specific reason. Never scored, never acceptable.

Fingerprint: SHA-256 of canonical sorted checker inputs (people, vehicles, places, deliveries, routes, finish time, problem sizes). Timestamps and status marks excluded. Identical normalized checker inputs, including entity IDs, get the same fingerprint; changing a problem size changes it.

Checker: What It Models and How It Decides

What the checker models

  • People: available from / until. Can drive or not. Holds the key or not. Cannot be in two places at once.
  • Vehicles: available from a time. One route at a time.
  • Places: one_vehicle_at_a_time controls capacity, not place identity. The checker needs one unambiguous loading area, inferred from its capacity/key role, a sole place, or a unique supply destination. Ambiguous places return question marks. The area has an opens_at time (planned loading start), and opens only from the later of that time and the earliest key holder's presence (if needs_key). "Place blocked" starts at opens_at for the chosen minutes.
  • Deliveries: loading cannot start before the delivery arrives.
  • Routes: households, load_minutes (needs a loader), drive_minutes (needs a driver and a vehicle). Jobs are filled only from driver_ids and loader_ids listed on the route - drivers primary first, then listed backups; loader lists are eligible sets with no priority. No one else may fill those jobs.
  • Start times can move freely within people's and vehicles' availability windows.
  • Finish time is a soft deadline; the solver minimises total households-times-minutes-late.

The real Ravi driver card is turned down: Ravi already drives Route C and loading still fails. The checker proves “Van back 10:45. Loading team gone.”

How the checker decides

After proving the minimum lateness cost, a second solve holds that cost fixed and minimises the sum of loading and driving start times. This removes arbitrary idle time without trading away the proven verdict. Both passes share the deterministic solver budget. If the second pass reaches its limit, retain the proven lateness verdict and the best valid timeline; earliest-start optimality is then not claimed. A question mark means the primary lateness verdict could not be proved. Small-model presolve probing reduces overhead. Warm local example runs have measured below three seconds; cold native-library import and host load can take longer.

tick Proven zero lateness. Zero is the floor; finding zero proves the plan genuinely survives.

cross Proven minimum above zero. That minimum is the human cost, proved optimal. E.g. “Route A: 10 households not delivered” or “Route C: 8 households not delivered.” Routes that cannot run (no driver, loading area cannot open) use a "not delivered" penalty of households times the full horizon (finish time + 180 min), keeping every scenario feasible. Human cost reads "Routes A, B, C: 30 households not delivered. Nobody can open the loading area"

qmark Deterministic time limit hit before the minimum lateness is proved. Uses max_deterministic_time, not wall clock, so the limit measures solver work; repeatability is tested with the locked inputs and solver version. Never a pass. Listed by name under "What was NOT tested."

Run order

Singles run first, in problem-id order. Any pair containing a single already marked cross is marked dimmed without solving. Valid because every problem type only removes options; a pair can never do better than its worst single. Remaining pairs are solved. One solver worker, fixed seed.

test_checker_monotone.py asserts on the example map that every pair's lateness is at least each of its singles'. The locked test also asserts the example produces no question marks.

Explain and Fix prd.md › Fix Cards and Scoring

One AI request per uncached broken case. POST /api/suggest-fixes uses the session-owned confirmed map and checker facts: failing problem ids, timeline, late routes, lateness, or "not delivered". Gemini is primary by default, with one Groq fallback on a transient provider or output-format failure. The AI returns an explanation and up to three suggestions; every operation is gated and every allowed fix is scored across the full grid. Successful responses are cached by session owner, fingerprint and scenario ID; failures do not become successful cache entries.

Request fields: fingerprint, scenario_id, optional live: true to ask AI instead of saved responses, and retry: true for one explicit retry after a live response has no eligible AI card. Live-pasted maps use live suggestions by default. Responses expose can_retry; provider errors include checker-only case_detail, keeping timeline and costs visible while AI is unavailable.

The checker's facts remain visible next to the labelled AI explanation. All three van + Anita leaves early cards fail: Anita's operation shortens 12:00 to 11:00, Ravi already drives C while loading fails at 10:45, and moving vehicles fixes three crosses but creates a supply-late single. The real Sam loader card on van + Anita absent fixes both van crosses. Joel's one spare key reveals Joel + Ravi absent. Coordinator-built spare keys for Maya and Sam, then Sam as Route A backup, finish at all 100 survived. Reasons come from operations and checker results, never the AI.

Data Model

Checker/fix shapes are Pydantic v2 models with extra="forbid"; review/report payloads are built by their server modules. Client contracts are maintained in web/src/types.ts beside the API client and checked by the production TypeScript build. Automatic OpenAPI generation is deferred.

AI output only AIPlanReading
  • people, vehicles, places, deliveries, routes
  • finish_time + nullable finish_time_source + guessed
  • questions: list of {item_id, question_text}
  • is_distribution_plan + reason
  • Each entity: id, name, timing fields, entity-mention source_line, closed fact_sources object, guessed
  • Routes: driver_ids (primary first), loader_ids

Never contains fingerprint, fix history, or server metadata.

Server-owned PlanMap
  • fingerprint (SHA-256 after confirm)
  • ai_meta: provider, model, timestamp
  • Wraps reading entities as Map* types
  • Each Map* adds: status, original_value
  • problem_sizes: dict[type_id, minutes]
  • fix_history: list[AppliedFix]

Never sent to the AI.

reading-v2 / read-v4 require every entity's fact_sources object and all its defined nullable fields in outgoing structured-output schemas, including Groq's strict schema. Each field cites its own value or assignment, or is null; unknown source fields are rejected. Older raw captures without fact_sources parse to null per-field sources. Their entity mentions are not promoted into field evidence.

AppliedFix records from_fingerprint and to_fingerprint so the report and Before/After toggle can reconstruct the full chain from the original plan to the current state by following fix_history.

State storage: no database. Review drafts, maps, results, suggestions and typed keys stay in server memory, associated with the session owner. Maps/results use fingerprints; successful suggestions also use scenario IDs. Keys never enter map data, fingerprints, logs, files or responses. Closing a tab does not clear server memory. /demo calls POST /api/demo/reset, clears browser storage and replaces the page with /. The endpoint clears only that browser's typed keys, reviews, maps/results/evidence/ancestors/suggestion batches and scoped fix caches, then rotates its HttpOnly SameSite=Lax cookie. Responses use Cache-Control: no-store. Revision bumps and active-owner guards prevent late reads or scoring responses from restoring discarded state. Other browsers and trusted unowned helpers are unaffected. Server restart clears every session; environment keys remain in local ignored .env.

Important Failure Modes prd.md › States and Boundaries

  • x
    Both AI providers fail. Clear error message, retry button, "try the example plan instead." Applies to both read-plan and suggest-fixes paths.
  • x
    Primary HTTP 503, timeout or rate limit. One attempt on the available fallback provider, then display the provider/model that answered. If neither succeeds, stable error_code plus safe plain detail; never reveal a key or raw provider request.
  • x
    AI output fails the format gate. Specific rejection reason (e.g. "Unknown person id 'dave' in route_a driver_ids"), retry button. Nothing unchecked reaches the plan map.
  • x
    A fix suggestion fails the gate. Card shows "Couldn't apply" with specific reason. Never scored, never acceptable.
  • x
    is_distribution_plan is false. Shows the AI's reason. Offers to load the example.
  • ?
    Solver hits the deterministic time limit. Question mark cell. Listed under "What was NOT tested." Never a pass.
  • !
    Plan exceeds 24 problems. Rule message on Screen 2 before Confirm: "This version supports up to 24 problems. This plan has N."
  • !
    Plan text exceeds ~4,000 characters. Counter turns amber at 3,500, red at 4,000, submit disabled above.
  • x
    Missing or invalid AI key. Clear error, retry and example actions. Invalid-key responses do not silently switch providers.
  • x
    No eligible AI fixes. Keep checker facts visible, show "None of these suggestions worked" and offer "Ask for new suggestions" once for a live case with a key. Coordinator-built changes remain available in either mode. Failed requests remain retryable; reopening a successful cached case never silently regenerates suggestions.

Decisions and Open Issues

CP-SAT for the checker

Lateness is a proved minimum, not a found example. CP-SAT's optimality proof is what makes the three honest answers possible. A heuristic solver could find a good schedule but not prove it is optimal. Tradeoff: heavier dependency than a hand-written scheduler.

Every scenario kept feasible with a "not delivered" penalty

Routes that cannot run carry a penalty lateness of households times the full horizon (finish time + 180 min). Unproved or ambiguous outcomes return a question mark; proved outcomes state their human cost. Human cost is always statable. Tick, cross, and question mark keep their meaning - there is no fourth state.

Id normalisation after the gate

AI-assigned ids are rewritten to stable type-and-name slugs after validation. Unchanged extracted labels and checker inputs normalize consistently when only AI-assigned IDs change. Different names can produce different person/vehicle IDs; reading equivalence is scored separately after role alignment. Duplicate ids are rejected by the gate.

AIPlanReading and PlanMap are separate schemas

The reading schema never asks the provider to create the server's fingerprint, fix history or status marks. Suggestion context includes scenario results and their map fingerprint, an identifier rather than a credential. Groq strict mode is workable because the AI schema contains only what the AI knows. The boundary between AI output and server state is explicit in code.

Pydantic extra="forbid" with nullable fields

Satisfies Groq strict mode (all fields required, no extra properties) while working identically for Gemini. One schema serves both providers.

Rules implemented only in Python

One implementation, tested in pytest. Corrections call POST /api/update-map against the server-owned draft. No duplicate browser rules.

Fingerprint hashes only checker inputs

People, vehicles, places, deliveries, routes, finish time, problem sizes - sorted canonically. Excludes timestamps and status marks. Identical normalized checker inputs, including entity IDs, get the same fingerprint; changing a problem size changes it.

Singles before pairs; dimmed pairs skipped without solving

Every problem type only removes options. Skipping is correct; test_checker_monotone.py asserts it on the example. The locked test asserts the example has no question marks.

Deterministic time limit (max_deterministic_time) not wall clock

Repeatability is tested with the locked inputs and solver version. Cross-platform identity is not established by those local tests.

One AI call returns both explanation and fix suggestions

Fewer round trips. The explanation and fixes are consistent because they came from the same context. Checker facts are always shown regardless.

Turned-down reasons from the checker, not the AI

The checker knows which resource the late route was waiting on. A machine-derived reason is more honest and more useful than a generated one.

Preview draws from stored fix results

suggest-fixes returns full per-scenario results and server-derived scores. Eligibility requires the selected case to survive, no new cross, and no unknown candidate results. Unknown outcomes receive no credit as fixed. Preview renders stored results without solving. Accepting a previewed fix replays from the cache.

example-truth.json is hand-authored; locked test runs against it

The locked test does not depend on the AI. Checker and locked test can be built and pass before any AI work. bakeoff compares providers against the truth map, not against each other, avoiding circularity.

One Genuine Uncertainty - Discussed and Resolved Correction cascades in the validation gate

When a user corrects Ravi's role to "can't drive," any route with Ravi as driver should lose its confirmed mark. The question was how the rules handle this without re-running the AI.

Agreed answer: entities are referenced by internal id. The rules engine walks the whole map on every change and flags any item whose constraints are no longer satisfied. No partial re-run; the whole map from scratch, every time.

Verified by: test_rules.py flips a person's can_drive to false after their route is confirmed, and asserts the route loses its confirmed mark and a rule fires reporting a missing driver.
