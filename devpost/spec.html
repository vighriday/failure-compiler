How This Works, In Plain Language

The app is a browser page talking to a small Python server running on your laptop. The server binds to 127.0.0.1 only, because it holds AI keys in memory.

When you paste a plan, the server sends it to an AI (Groq first, Gemini as a fallback). The AI reads messy text and returns a structured description of the plan: who is doing what, in what vehicle, at what place, between what times. The AI returns an AIPlanReading. The server wraps it into a PlanMap, adding its own metadata. The two schemas are separate so Groq strict mode never forces the AI to invent a fingerprint or a fix history.

That description comes back as JSON and the server runs it through a strict format check before it touches anything else. This is the core learning goal made concrete: the AI produces output, the gate decides whether it is usable, and nothing downstream ever sees an unchecked map.

The browser calls POST /api/validate-map on every correction (debounced, fast, same Python code that runs at Confirm). Rules are implemented once, in Python. No TypeScript reimplementation.

The checker is a constraint solver (CP-SAT). Singles run first. Any pair that contains a broken single is marked dimmed without solving. For remaining pairs, the solver finds the best possible schedule using only the people and vehicles the plan names. Zero lateness proved = tick. Minimum above zero proved = cross, with that minimum as the human cost. Some scenarios leave a route with no driver or the loading area with no key holder; rather than failing with no number, every route may be "not delivered," carrying a penalty larger than any possible lateness (households times the full horizon). The solver always returns a number. Deterministic time limit hit = question mark, never a pass.

After the format gate, the server normalises all entity ids to stable slugs from type and name (person-ravi, vehicle-van, route-c) and updates every reference. Two runs of the same plan always produce the same ids and the same fingerprint.

Clicking a cross triggers one AI call that returns both a plain explanation sentence and up to three fix suggestions. The server caches the result per fingerprint and scenario, so reopening a cross never calls the AI again. The checker's facts are always shown; the AI sentence sits next to them, labelled. Turned-down reasons come from the checker. Preview draws from stored fix results without re-solving.

Problem Type Taxonomy

Fixed list. Each type applied to every matching entity in the confirmed map, producing one concrete label per entity. Sizes from preset choices only: 15, 30, 45, 60, 90 minutes.

Volunteer absent Each volunteer · No size

Person unavailable for the whole run. E.g. "Ravi absent."

Volunteer leaves early Each volunteer · Default 90 min

available_until reduced by size. E.g. "Sam leaves 90 min early."

Vehicle returns late Each vehicle · Default 30 min

available_from pushed back by size. E.g. "Van returns 30 min late."

Supply delivery arrives late Each delivery · Default 45 min

Loading blocked until delivery + size. E.g. "Supply truck 45 min late."

Place blocked Each place · Default 30 min

Place unavailable for first size minutes. E.g. "Loading area blocked 30 min."

Example plan: Route A has 10 households, Route B has 12, and Route C has 8. The van returns from an early pickup at 9:30; Joel has the only key and leaves at 10:30; Maya leaves at 10:45; Sam is not on the loading team. Hidden pairs: Supply truck late + Ravi absent; Van late + Anita leaves early; Van late + Anita absent.

Count: 5 volunteers x 2 types + 2 vehicles + 1 delivery + 1 loading area = 14 problems. 14 singles + 86 pairs = 100 tests: 1 single weak spot, 3 hidden pairs, 12 dimmed, 84 survived.

Hall key: modelled as holds_key: true on Joel. "Joel absent (only key holder)" is the single weak spot. The loading area rule checks holds_key.

Cap: 24 problems. Exceeding the cap shows a rule message before Confirm.

Deliberately out of scope: volunteer arrives late. Listed under "What was NOT tested" in every report.

The Validation Gate prd.md › Plain Rules Validation

The learning goal made concrete: AI produces output → gate checks it → human confirms → checker acts. Every AI output passes through the same gate.

1
Parse JSONMalformed JSON rejected immediately with the parse error.
2
Pydantic validationextra="forbid", all fields required. Missing field, extra field, wrong type: rejected with the field name.
3
Reference integrityEvery person, vehicle, place id used in routes and jobs must exist in the entity lists. Unknown id rejected with the offending value.
4
Plain rulesEvery route has a driver id and a vehicle id. Every time is coherent. Finish time is explicit. Problem count within cap. Failures surface as questions on Screen 2; never silent.
5
Human confirmsConstrained inputs only. Every correction triggers POST /api/validate-map (debounced 150 ms, same Python rules). Affected items lose their confirmed mark. Confirm button computed from live state.
6
Server re-validates on ConfirmBrowser call is for speed; server is the authority. Checker endpoint refuses any map that fails.

Rules re-run on every change, not only at Confirm. Entities are referenced by internal id. If a correction changes something other items depend on (e.g. Ravi corrected to "can't drive"), those items lose their confirmed mark and show "check this, Ravi changed." The whole map is re-validated from scratch each time.

Fixes go through the same gate. A fix that fails shows as "Couldn't apply" with the specific reason. Never scored, never acceptable.

Fingerprint: SHA-256 of canonical sorted checker inputs (people, vehicles, places, deliveries, routes, finish time, problem sizes). Timestamps and status marks excluded. Two identical plans get the same fingerprint; changing a problem size changes it.

Checker: What It Models and How It Decides

What the checker models

  • People: available from / until. Can drive or not. Holds the key or not. Cannot be in two places at once.
  • Vehicles: available from a time. One route at a time.
  • Places: one vehicle loading at a time. Each place has an opens_at time (planned loading start). The loading area can only be used from the later of opens_at and the earliest time a key holder is present (if needs_key). "Place blocked" means blocked from opens_at for the chosen minutes.
  • Deliveries: loading cannot start before the delivery arrives.
  • Routes: households, load_minutes (needs a loader), drive_minutes (needs a driver and a vehicle). Jobs are filled only from driver_ids and loader_ids listed on the route - primary first, then listed backups. No one else may fill those jobs.
  • Start times can move freely within people's and vehicles' availability windows.
  • Finish time is a soft deadline; the solver minimises total households-times-minutes-late.

The checker evaluates “Add Maya as backup driver for Route C” and turns it down because the gap is loading, not driving. Its reason is “Van back 10:45. Loading team gone.”

How the checker decides

tick Proven zero lateness. Zero is the floor; finding zero proves the plan genuinely survives.

cross Proven minimum above zero. That minimum is the human cost, proved optimal. E.g. “Route A: 10 households not delivered” or “Route C: 8 households not delivered.” Routes that cannot run (no driver, loading area cannot open) use a "not delivered" penalty of households times the full horizon (finish time + 180 min), keeping every scenario feasible. Human cost reads "Routes A, B, C: 30 households not delivered. Nobody can open the loading area"

qmark Deterministic time limit hit before either is proved. Uses max_deterministic_time, not wall clock, so results are the same on every machine. Never a pass. Listed by name under "What was NOT tested."

Run order

Singles run first, in problem-id order. Any pair containing a single already marked cross is marked dimmed without solving. Valid because every problem type only removes options; a pair can never do better than its worst single. Remaining pairs are solved. One solver worker, fixed seed.

test_checker_monotone.py asserts on the example map that every pair's lateness is at least each of its singles'. The locked test also asserts the example produces no question marks.

Explain and Fix prd.md › Fix Cards and Scoring

One AI call per broken case. POST /api/suggest-fixes sends the confirmed map plus the checker's facts (failing problem ids, timeline, late routes, lateness in minutes, or "not delivered" if applicable). The AI returns one plain explanation sentence and up to three fix suggestions in one response. The server caches the result keyed by fingerprint and scenario id - reopening a cross never calls the AI again.

The checker's facts are always shown in the panel. The AI sentence sits next to them, labelled "AI's explanation." “Add Maya as backup driver for Route C” is turned down because the gap is loading, not driving; the checker gives “Van back 10:45. Loading team gone.” The fixes are “Sam loads Route C” and “Sam backs up Route A.” One spare key is turned down because it reveals Joel absent + Maya absent; spare keys for Maya and Sam make all 100 scenarios survive.

Fix operations (fixed list, always gateable)

Fixes are composed of one or more of these operations. No new people or vehicles may be invented; references always resolve.

OperationWhat it changes
Add or replace a driver on a routedriver_ids on a Route, from existing Person ids
Add or replace a loader on a routeloader_ids on a Route, from existing Person ids
Move a route to another vehiclevehicle_id on a Route, from existing Vehicle ids
Change a person's availabilityavailable_from or available_until on a Person
Change a vehicle's availabilityavailable_from on a Vehicle
Give the key to another personholds_key: true on one Person, false on the current holder

Scoring and preview

suggest-fixes returns each fix's full list[ScenarioResult]. The browser derives fixes_n, still_broken_n, new_crosses_n from those results. Preview draws the projected grid directly from the stored results - no re-solve in the browser. Accepting a previewed fix replays from the cached results with the flip animation; any cell not in the cache re-solves.

Example mode saved fixes

fixtures/example-fixes.json stores the explanation and per-scenario results for each broken case. They still pass through the gate and are scored live. If a broken case appears with no saved suggestion, the panel says: "No saved suggestions for this case. Add a key to ask the AI."

Data Model

All shapes in server/models.py as Pydantic v2 with extra="forbid". TypeScript types generated via openapi-typescript. Neither side can drift.

AI output only AIPlanReading
  • people, vehicles, places, deliveries, routes
  • finish_time + source_line + guessed
  • questions: list of {item_id, question_text}
  • is_distribution_plan + reason
  • Each entity: id, name, timing fields, source_line, guessed
  • Routes: driver_ids (primary first), loader_ids

Never contains fingerprint, fix history, or server metadata.

Server-owned PlanMap
  • fingerprint (SHA-256 after confirm)
  • ai_meta: provider, model, timestamp
  • Wraps reading entities as Map* types
  • Each Map* adds: status, original_value
  • problem_sizes: dict[type_id, minutes]
  • fix_history: list[AppliedFix]

Never sent to the AI.

AppliedFix records from_fingerprint and to_fingerprint so the report and Before/After toggle can reconstruct the full chain from the original plan to the current state by following fix_history.

Provenance on every item

MapPerson (wraps AIPerson, adds):
  status:         "unconfirmed" | "confirmed" | "corrected" | "added"
  original_value: AIPerson | None   # AI's original reading, for the strikethrough

# "added" = created by a rule question, not the AI
# Summary "AI read 24 items, 2 corrected, 1 added" computed from status counts

Checker entity shapes

Person          id, name, available_from, available_until, holds_key
Vehicle         id, name, available_from
Place           id, name, opens_at (planned loading start, minutes), one_vehicle_at_a_time (always true), needs_key
Delivery        id, name, arrives_at (minutes), place_id
Route           id, name, households, load_minutes, drive_minutes,
                vehicle_id, driver_ids (primary first), loader_ids (primary first)

Derived from PlanMap at run time. The checker may only assign jobs from driver_ids and loader_ids on each route.

scenario_id:           str
failures:              list[str]        # Problem ids
state:                 "tick" | "cross" | "dim" | "qmark"
dim_cause:             str | None       # Problem id of the single that causes dimming
lateness_minutes:      int | None       # Minutes, not seconds
lower_bound_minutes:   int | None
timeline:              list[TimelineEvent]

map_fingerprint:       str

FixSuggestion

id, description

State storage: no database. Confirmed maps, test results, and fix results held in server memory keyed by fingerprint. Closing the tab loses the session - by design.

bakeoff.py: runs the example plan through both providers three times. For each, normalises the ids, then compares the raw reading against example-truth.json field by field - reporting the percentage that match and a list of mismatches. Important Failure Modes prd.md › States and Boundaries

  • x
    Both AI providers fail. Clear error message, retry button, "try the example plan instead." Applies to both read-plan and suggest-fixes paths.
  • x
    AI output fails the format gate. Specific rejection reason (e.g. "Unknown person id 'dave' in route_a driver_ids"), retry button. Nothing unchecked reaches the plan map.
  • x
    A fix suggestion fails the gate. Card shows "Couldn't apply" with specific reason. Never scored, never acceptable.
  • x
    is_distribution_plan is false. Shows the AI's reason. Offers to load the example.
  • ?
    Solver hits the deterministic time limit. Question mark cell. Listed under "What was NOT tested." Never a pass.
  • !
    Plan exceeds 24 problems. Rule message on Screen 2 before Confirm: "This version supports up to 24 problems. This plan has N."
  • !
    Plan text exceeds ~4,000 characters. Counter turns amber at 3,500, red at 4,000, submit disabled above.

What Was Simplified and Why

  • No persistence.Fingerprint makes a single session reproducible within itself. Persistence is post-PoC.

Decisions and Open Issues

CP-SAT for the checker

Lateness is a proved minimum, not a found example. CP-SAT's optimality proof is what makes the three honest answers possible. A heuristic solver could find a good schedule but not prove it is optimal. Tradeoff: heavier dependency than a hand-written scheduler.

Every scenario kept feasible with a "not delivered" penalty

Routes that cannot run carry a penalty lateness of households times the full horizon (finish time + 180 min). The solver always returns a number. Human cost is always statable. Tick, cross, and question mark keep their meaning - there is no fourth state.

Id normalisation after the gate

AI-assigned ids are rewritten to stable type-and-name slugs after validation. Two runs of the same plan always produce the same ids and the same fingerprint. Duplicate ids are rejected by the gate.

AIPlanReading and PlanMap are separate schemas

The AI never sees the server's fingerprint, fix history, or status marks. Groq strict mode is workable because the AI schema contains only what the AI knows. The boundary between AI output and server state is explicit in code.

Pydantic extra="forbid" with nullable fields

Satisfies Groq strict mode (all fields required, no extra properties) while working identically for Gemini. One schema serves both providers.

Rules implemented only in Python

One implementation, tested in pytest. The browser calls POST /api/validate-map. No drift possible.

Fingerprint hashes only checker inputs

People, vehicles, places, deliveries, routes, finish time, problem sizes - sorted canonically. Excludes timestamps and status marks. Two identical plans get the same fingerprint; changing a problem size changes it.

Singles before pairs; dimmed pairs skipped without solving

Every problem type only removes options. Skipping is correct; test_checker_monotone.py asserts it on the example. The locked test asserts the example has no question marks.

Deterministic time limit (max_deterministic_time) not wall clock

Results are machine-independent. A slower machine cannot turn a result into a question mark.

One AI call returns both explanation and fix suggestions

Fewer round trips. The explanation and fixes are consistent because they came from the same context. Checker facts are always shown regardless.

Turned-down reasons from the checker, not the AI

The checker knows which resource the late route was waiting on. A machine-derived reason is more honest and more useful than a generated one.

Preview draws from stored fix results

suggest-fixes returns full per-scenario results. Preview is a render operation, not a solve operation. Accepting a previewed fix replays from the cache.

example-truth.json is hand-authored; locked test runs against it

The locked test does not depend on the AI. Checker and locked test can be built and pass before any AI work. bakeoff compares providers against the truth map, not against each other, avoiding circularity.

One Genuine Uncertainty - Discussed and Resolved Correction cascades in the validation gate

When a user corrects Ravi's role to "can't drive," any route with Ravi as driver should lose its confirmed mark. The question was how the rules handle this without re-running the AI.

Agreed answer: entities are referenced by internal id. The rules engine walks the whole map on every change and flags any item whose constraints are no longer satisfied. No partial re-run; the whole map from scratch, every time.

Verified by: test_rules.py flips a person's can_drive to false after their route is confirmed, and asserts the route loses its confirmed mark and a rule fires reporting a missing driver.
