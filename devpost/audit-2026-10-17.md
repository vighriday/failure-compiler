## Defects found outside the passing tests

The following are confirmed findings. Their fixes have not been implemented during this audit.

### 1. The server does not enforce complete human confirmation

**Priority: repair before live AI.**

The normal browser flow blocks unconfirmed items correctly. However, sending `/api/confirm-map` only a `plan_map`, with no `items`, `questions` or `answers`, returns HTTP 200 and a fingerprint. The example's entity statuses are still unconfirmed. Missing lists default to empty lists, so the server treats them as having nothing left to confirm.

In plain language: the visible door is locked, but the server accepts a request that skips the checklist. The approved pipeline requires the server to enforce this boundary itself.

Relevant code: [confirmation handler](../server/main.py#L84). A repair needs server-owned knowledge of the expected items/questions and their confirmation state, plus tests that omissions and forged incomplete lists cannot bypass confirmation.

### 2. Same-plan fingerprints can reuse incompatible cached results

**Priority: repair before live AI.**

The fingerprint correctly ignores collection ordering. But scenario IDs depend on the order in which people/problems are listed, and `remember_map` can replace the map while keeping results already cached under that fingerprint.

A direct probe cached the original truth map, reversed its people/routes and stored it again. The fingerprint stayed equal, as required. **Twenty cached result IDs did not occur in the new scenario list.** The browser uses those IDs to place cells, so this can leave results unmatched or prevent finding the intended case.

In plain language: the identity tag says “same plan,” while the result labels have changed. The runtime map, scenario IDs and cache need the same canonical ordering.

Relevant code: [scenario generation](../server/checker/scenarios.py#L51), [session reuse](../server/session.py#L19), [fingerprinting](../server/validation/fingerprint.py#L13). The existing fingerprint tests check hash equality, not this replay behavior.

### 3. Editing through the Read tab can block re-confirmation

**Priority: repair before the next hands-on demo.**

Reproduction:

1. Complete the example and run the checker.
2. Use the top **Read** tab, rather than the **Plan map** return button.
3. Change “Vehicle returns late” from 30 to 45 minutes.

The page shows “Out of date: re-run,” but the main button still says **Plan confirmed** and remains disabled. That path does not reset all the confirmation/screen state. Validation also depends on the separate `screen` value, which top-tab navigation does not update consistently.

Relevant code: [validation effect](../web/src/App.tsx#L111), [size edit](../web/src/App.tsx#L384), [disabled confirmation](../web/src/App.tsx#L399). The current browser checks return via **Plan map**, so they miss this path.

### 4. Accepted fixes leave some displayed facts out of date

**Priority: repair before the next hands-on demo.**

After accepting spare keys for Maya and Sam, returning to the map still displays **“Joel has the only loading-area key.”** The checker map contains the new keys; some displayed sentences are still the original handwritten statements. Fix badges alone do not make those sentences correct.

Reading text, correction history and checklist summaries should be derived from the updated map, while preserving the original statement separately as provenance.

Relevant code: [statement rendering and fix notes](../web/src/App.tsx#L338), [accepted map update](../web/src/App.tsx#L409). The story test checks the “changed by Fix” badges, but not every sentence after a fix.

### 5. General map correction is only partly built

**Priority: complete before handling arbitrary AI readings.**

There are 24 reading rows, but only **two** have a general **Correct** control: Ravi's ability to drive and Route C's duration. The three Ravi driver-rule pickers and the loading question also work. Most people/times/vehicles/route facts can be confirmed but cannot be corrected. No general time-picker implementation exists.

The screen is sufficient for the scripted demonstration corrections. It does not yet meet the broader PRD behavior of correcting an arbitrary reading using constrained inputs. Some problem counts, names and timeline dimensions are also tied to the example.

Relevant code: [two special correction cases](../web/src/App.tsx#L336), [example-specific timeline](../web/src/components/CaseTimeline.tsx).

### 6. Input validation needs consistent boundary handling

**Priority: repair before live AI.**

Confirmed probes:

- A duplicate person ID is reported as valid by `/api/validate-map`, then produces HTTP 500 during confirmation instead of a clear validation response.
- A map with no people, routes, vehicles, places or deliveries can be confirmed.
- A person's negative availability start time produces no rule violation.
- The AI schema converts strings such as `"540"` and `"false"` into an integer and boolean. `extra="forbid"` rejects extra fields; it does not by itself enforce strict scalar types.

The standalone gate catches duplicate IDs, but the HTTP boundary does not consistently apply it and handle its errors. The correct repair is a consistent gate and explicit rules for supported inputs. It does not require extending the checker model.

Relevant code: [HTTP validation](../server/main.py#L62), [map models](../server/validation/models.py), [rules](../server/validation/rules.py).

### 7. Documents and code still disagree in specific places

**Priority: cleanup before submission.**

- `spec.html` says giving someone the key sets the current holder's `holds_key` to false. The canonical Markdown and code correctly give an additional spare key.
- `prd.html` names the revised fixes but still shows old illustrative card scores: “Fixes 2 / Still broken 0” for a combination now described as clearing all three hidden pairs.
- Scope/PRD/spec describe the final saved AI reading. The checklist and README correctly disclose today's handwritten placeholder. A clearer current-status note would prevent readers confusing the target with the implementation.
- The spec describes generated OpenAPI TypeScript types and a reducer/context structure. The app currently has handwritten types, broad `any` entity shapes and state largely in `App.tsx`.
- Closing the tab loses browser state, but server-side maps/results/suggestions remain in memory until the process ends. There is no tab-close cleanup. Some privacy wording implies immediate complete deletion.
- The README links to eight missing images/GIFs and one missing sample PDF; its video URL and personal “Why I built this” section are placeholders.
- Smaller polish gaps include the planned amber/red character-counter thresholds and example-specific timeline labels/scaling.

### 8. Repository checks need a cleanup pass

**Priority: before final sign-off.**

Full lint reports 20 issues in `scripts/check_map.py`, `server/checker/solver.py`, `server/config.py`, `server/grid.py`, `server/main.py` and `server/models.py`. These are mostly maintenance issues, and the passing runtime tests establish that they have not broken the demonstrated example. They still mean the documented lint command does not pass.

The untracked local hook calls `npx tsc --noEmit`. At the root solution configuration that command lists no source files; the actual `npm run build` command correctly checks both TypeScript projects. The hook was left unchanged.
